# Project Rules

## Workflow
1. Plan first. For any non-trivial task, enter plan mode before writing code. Write the plan to `docs/plan_<topic>.md` — include context, file list, steps, error handling, acceptance criteria, and key test cases (edge cases included). Ask clarifying questions before finalising; do not assume intent. When modifying an existing feature, update its plan file first, then implement.
2. Before a plan is approved, "ok / go ahead / do it" means proceed to planning. After the plan is approved, it means implement the approved plan.
3. Implement → test → reports → changelog → done. Test tiers and report templates: see the `testing-and-reports` skill. Documentation rules: see the `project-docs` skill.
4. Read existing code before modifying it. Deliver what was asked, at the scope intended. Make routine judgment calls yourself; check in only when different readings of the request would lead to materially different work. If the request seems mistaken or a better approach exists, say so in a sentence and continue as asked rather than quietly narrowing, widening, or transforming it. Prefer editing existing files; required project docs are the exception.
5. Finish the whole task before handing it back. (No separate "double-check" or "re-verify" step is needed — verification happens as part of doing the work; see Verification below.)

## Model Convention
- Plan phase: Fable. Execution: Opus (Opus 5). The user switches the main model manually with `/model`; Claude does not switch it itself.
- Effort is the primary cost/latency control on Opus 5. Default is `high`. Use `low`/`medium` liberally for routine edits, review passes, and mechanical work where quality holds; step up to `xhigh` only for demanding coding or long-horizon agentic work. The user sets effort with `/model`; Claude does not need explicit re-check or verification steps to compensate at lower effort.
- Subagents run per role, set in each agent's `model` frontmatter (`.claude/agents/`): explorer → haiku, implementer → sonnet, reviewer → opus. No blanket subagent model override — each agent picks the cheapest model that fits its task.

## Subagents
- Delegate only for large tasks that are genuinely independent and parallelizable — a wide multi-file investigation, separate modules, or distinct test categories. Do not delegate work you can finish yourself in a handful of tool calls, and do not spawn subagents to verify or double-check your own work. If one subagent can do it, use one, not several. Keep spawn counts low.
- Predefined roles live in `.claude/agents/`: `explorer` (read-only search), `implementer` (code against an approved plan), `reviewer` (independent quality + security review). Prefer these over ad-hoc agents. The reviewer is a genuine second pass on code the main session wrote — that is a real independent track, not self-verification.
- Launch independent agents in a single message. Each agent prompt must be self-contained (file paths, context, clear instructions) — agents have no memory of this conversation.
- After agents complete, synthesise results and resolve conflicts across modules. If an agent fails, diagnose and re-spawn with corrected instructions — do not retry blindly.

## Project Structure
- `src/` — source code, subdirectories by feature or layer. `tests/` — mirrors `src/`; no test files inside `src/`; `tests/fixtures/` holds synthetic schema-matching sample data. `data/` — public game data collected by the scrapers (poe2db.tw, PathOfBuilding-PoE2, poe.ninja); readable, regenerated by code, never hand-edited. `docs/` — plans, reports, project docs. `output/` — program-generated files (logs, exports, metrics); never in the project root.
- Root files only: `README.md`, entry points (`main.py`, `index.ts`, `app.py`, ...), and config (`pyproject.toml`, `uv.lock`, `.env`, ...).

## Packaging
- The product is a stdio MCP server and a Claude Code plugin, started by the user's AI client with `uv run`. No Docker image, no web UI, no hosted service.
- Anything a client needs at start-up must work on Windows, macOS and Linux and must not write to stdout (stdout carries the MCP protocol).

## Code Style
- Small, single-purpose functions. Readable over clever; three similar lines beat a premature abstraction.
- Constants at the top of the file in a clearly marked block. Never silence exceptions with a bare `except` / `catch` — be specific.
- Comments only where the logic is not self-evident. Do not add docstrings, comments, or type annotations to code you did not change.

## Git
- Never commit or push without explicit user instruction (also enforced via `ask` rules in `.claude/settings.json`). No amend or force-push unless explicitly asked.
- Commit messages explain the "why", not just the "what".

## Verification
- Do not add explicit "verify your work", "double-check", or "re-verify before responding" steps. Verification and self-correction happen as part of doing the work; mandating separate re-check passes wastes tokens without improving quality.
- Correct an earlier statement only when the error would change the user's code, conclusions, or decisions. State such corrections plainly and briefly, then continue. For slips that change nothing, fix and move on without noting it.
- Tests, reports, and the security scan (see `testing-and-reports` skill) are still required as deliverables where the tier calls for them — those are outputs the project needs, not redundant self-checks.

## Environment
- Windows shell is PowerShell: use `$env:VAR = "value"` (`set VAR=value` does not work for Python/Node to read). macOS/Linux: `export VAR="value"`.
- Use forward slashes in code paths; platform-specific slashes only in shell-specific docs.

## Communication
- Reply in the same language the user writes in. Keep responses focused, brief, and concise; keep disclaimers and caveats short and spend most of the response on the main answer. When asked to explain something, give a high-level summary unless depth is requested.
- During agentic work: before the first tool call, say in one sentence what you're about to do. While working, give a brief update only when you find something important or change direction. When finished, lead with the outcome first, supporting detail after.
- Match written deliverables (reports, docs) to what the task needs — cover the substance, don't pad with filler sections, redundant summaries, or boilerplate.
- Use tables and code blocks for structured information. Reference code locations as `file_path:line_number`.
