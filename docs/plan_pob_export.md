# 計畫：Phase 17 匯出到 Path of Building（第一段：職業、天賦、寶石）

2026-11-12 核准。沒有你的指示不 commit、不推送。

## 背景

plugin 現在能產生經過驗證的流派建議，但不計算傷害。Path of Building（PoB）會算，所以把
建議變成 PoB 能讀的「匯入碼」，使用者貼進 PoB 就能看到天賦樹、技能組合與計算結果。

你在 2026-11-12 的決定：

- 分兩段。**第一段：職業、昇華、天賦、寶石。第二段：裝備與詞綴。**
- 只產生匯入碼，**不寫任何檔案**。「直接寫進 PoB 的 `Builds` 資料夾」記為待辦，之後有
  需求再做成獨立、需使用者主動選擇的 plugin 指令。
- 不上傳到任何網站（pobb.in、poe2db 等）。

## 調查結果（只讀，使用本機新裝的 PoB 0.23.1）

| 發現 | 意義 |
|---|---|
| 匯入碼 = build 的 XML → zlib 壓縮 → base64（`+`、`/` 換成 `-`、`_`） | Python 標準函式庫就能產生，不需新的相依套件 |
| XML 的天賦是一串節點編號（`<Spec nodes="…" treeVersion="0_5">`） | 我們的天賦資料本來就取自 PoB 的 `tree.json`（0_5），編號直接可用 |
| 職業用 `classInternalId`（數字）、昇華用 `ascendancyInternalId`（如 `Ranger1`） | 昇華代號我們已有；職業數字代號目前沒存，蒐集天賦時要多存一欄 |
| 寶石用 `gemId`（如 `Metadata/Items/Gems/SkillGemIceNova`），找不到時退回用名稱 | 我們的寶石紀錄已有同一個欄位（`item_type`） |
| 寶石對照實測：技能 327 / 347、輔助 567 / 612、精魂 53 / 53 | 對不上的 65 顆多半是 PoB 這一版還沒收錄的新寶石與預設攻擊，匯出時列為「未放入」 |
| 我們的天賦節點有 168 個不在 PoB 0.23.1 裡 | 我們抓的是 PoB 開發中的版本，比正式版新；使用者的 PoB 太舊時這些節點會被 PoB 略過，回傳結果要說明 |
| PoB 沒有對外接口，發行版也沒有無介面模式 | 「PoB 真的讀得進去」只能由你在 PoB 貼上確認 |

## 設計

**1. 新工具 `export_pob`（唯讀，第十八個 MCP 工具）**

輸入：

| 參數 | 說明 |
|---|---|
| `class_name`、`ascendancy` | 與 `path_to` 相同，中英文皆可 |
| `targets` | 目標天賦，與 `path_to` 相同；工具內部用同一套路徑計算得到完整、相連的配點 |
| `skills` | 每筆是一組技能：`"主技能: 輔助一, 輔助二"`，最多 12 組、每組最多 5 顆輔助 |
| `main_skill` | 可選，哪一組是主要技能（預設第一組） |
| `title`、`lang` | 可選 |

輸出：

| 欄位 | 內容 |
|---|---|
| `code` | 匯入碼 |
| `summary` | 職業、昇華、用了幾點天賦、幾組技能、幾顆寶石 |
| `not_exported` | 沒放進去的東西與原因（查無此名稱、本機紀錄沒有遊戲代號、不能輔助該技能、到不了的天賦、PoB 沒有代號的昇華） |
| `notes` | 固定說明：寶石一律 20 級 0 品質、沒有裝備所以 PoB 的數字只反映天賦與寶石、天賦樹版本 0_5、PoB 要更新到最新版 |
| `how_to_import` | PoB 中「匯入/匯出 → 貼上 → 匯入」的步驟，依回答語言 |

規則：

- 每個名稱先用現有的驗證邏輯比對本機資料；查無的不會被寫進匯入碼。
- 輔助寶石是否能輔助該技能，沿用 `supports_for` 的資料檢查，不相容的列入 `not_exported`。
- 等級、寶石等級與屬性點：見下方「2026-11-12 修訂」。
- 不寫檔、不連網、不讀 PoB 的資料夾。

**2. 程式**

- `src/tools/pob_export.py`（新增）：組 XML（`xml.etree.ElementTree`）、壓縮編碼、
  以及一個反向的 `decode_code`（測試與除錯用）。
- `src/tools/build_tools.py`：`export_pob` 方法，重用 `path_to` 的路徑計算、
  `_class_and_ascendancy`、`gem_fact` 與既有的長度與數量上限檢查。
- `src/tools/mcp_server.py`：註冊工具（說明不超過 1,024 字元）。
- 天賦蒐集程式：在 `data/passive_tree/classes.json` 的每個職業多存 PoB 的數字代號；
  之後跑一次 `update passives`（7 個請求）。
- `src/tools/build_workflow.py`、`skills/poe2-advisor/SKILL.md`：流程最後加一步——流派寫完後
  呼叫 `export_pob`，把匯入碼附在回答最後，並說明它不含裝備。

**3. 更新 PoB 的指令 `/pobg:update-pob`（你在 2026-11-12 追加）**

匯入碼要在夠新的 PoB 才讀得完整，所以提供一個讓使用者更新 PoB 的指令。做法與我這次
替你更新的步驟相同，你的三個決定：下載到新資料夾、自動判斷是否含 PoeCharm2、路徑每次
由使用者提供。

- 形式：一個新的 skill（`skills/update-pob/SKILL.md`）加一支命令列程式
  `src/tools/pob_update.py`。skill 請 AI 用 `uv run python -m src.tools.pob_update` 執行；
  沒有 shell 的用戶端，使用者可以自己在終端機跑同一行指令（寫進 README）。
  不做成 MCP 工具：下載約 380 MB，會超過一次工具呼叫的時間，而且這是會寫檔的動作，
  應該只在使用者明確要求時執行。
- `--dir <資料夾> --check`：只讀取該資料夾的 `manifest.xml` 版本，向 GitHub 查最新版
  （2 個請求），回報「目前 / 最新」，不寫任何檔案。
- `--dir <資料夾>`（不加 `--check`）：
  1. 判斷類型：資料夾內有 `PoeCharm3.exe` 就是 PoeCharm2 加 PoB，否則是純 PoB。
  2. 已是最新就結束。
  3. 下載官方的 PoB Portable 壓縮檔，核對 GitHub 公布的 SHA-256；不符就中止並刪除下載檔。
  4. PoeCharm2 沒有正式發行版，下載它主分支最新一次提交的壓縮檔（沒有官方雜湊可核對，
     會在結果中說明）。
  5. 解壓縮到**旁邊的新資料夾**（名稱帶版本或日期）；新資料夾已存在就中止。
  6. 把舊資料夾存過的 build（`Builds/`）與 PoeCharm2 的語言設定**複製**過去。
     不複製 `Settings.xml`（裡面有帳號登入憑證），使用者要重新登入。
  7. 回報新資料夾位置、版本、複製了幾個 build。舊資料夾不修改、不刪除。
- 只寫入使用者給的資料夾的上一層；下載前檢查磁碟空間；解壓縮時拒絕會跳出目標資料夾
  的路徑；輸出不寫到 stdout 以外會影響 MCP 的地方（這支程式不經 MCP server）。

錯誤處理：資料夾不存在或裡面不是 PoB（沒有 `manifest.xml`）→ 說明並結束；下載失敗或
雜湊不符 → 刪除未完成的檔案與新資料夾，舊的不受影響；空間不足 → 下載前就中止。

測試（離線）：`tests/unit/test_pob_update.py` 用假的壓縮檔與假的下載——版本比對、兩種
資料夾類型、雜湊不符中止且不留檔、新資料夾已存在、build 與語言設定被複製而
`Settings.xml` 沒有、舊資料夾逐位元不變、惡意壓縮檔路徑被拒絕、`--check` 不寫檔。
真實驗證：對 `G:\POB\poe2\PoeCharm2-20260728` 跑 `--check`（應回報已是最新），
並對舊的 `PoeCharm2-20250410` 跑 `--check`（應回報 0.11.2 → 0.23.1）。

## 2026-11-12 修訂：角色等級、寶石等級、屬性需求

你在 PoB 實測後的決定。原則：這些都由程式查資料算出，不靠模型推論。

| 項目 | 做法 | 資料來源 |
|---|---|---|
| 角色等級 | 匯入碼寫入 PoB 自己會算出的等級（PoB 算完數值才定等級且不重算，寫 1 級會顯示 1 級的生命）。123 點對應 100 級。新參數 `character_level`（1–100）可指定等級；配點超過該等級可用點數時在 `notes` 說明 | PoB 的 `QuestRewards.lua`（`update passives` 多 1 個請求，共 8 個），存為 `classes.json` 的 `pob_level_acts` |
| 技能寶石等級 | 每顆技能／精魂寶石取「需求等級 ≤ 角色等級」的最高級（上限 20）；輔助寶石沒有等級 | 寶石紀錄的 `level_effects`（每一級的需求等級與屬性需求） |
| 屬性需求 | 與 PoB 相同：每顆技能寶石（該級的需求）各算一項，全部輔助寶石的加值（`+5 Dex`）跨各組加總算一項，取其中最大者（第三輪檢查依 PoB 程式修正；原本寫成相加） | `level_effects`、`requires_stats` |
| 已有屬性 | 職業基礎屬性 + 路線上天賦給的固定屬性（不含屬性天賦點） | PoB `tree.json` 的 `base_str/dex/int`（存為 `base_attributes`）、天賦屬性索引 |
| 屬性天賦點分配 | 逐點分給缺口最大的屬性；需求都滿足後，剩下的給主技能的屬性。傳入 `attribute` 時全部設為該屬性 | 以上三者 |
| 回報 | `summary.attributes` 列出每個屬性的「已有 / 需求」；仍不足的在 `notes` 說明要靠裝備補 | |
| 流程 | 流派建議選寶石時要考慮屬性需求；回答要說明哪些屬性需靠裝備 | 流程文字、skill |

第二輪獨立檢查（13 項，均為 Low / Info）一併處理：路線不得穿過其他職業的起點；免費昇華節點不計點數；
任務檔下載失敗不中止天賦更新；任務檔解析改為能處理巢狀表格；`update-pob` 的 `..` 路徑與唯讀資料夾錯誤。

## 錯誤處理

| 情況 | 行為 |
|---|---|
| 職業或昇華查無 | 與 `path_to` 相同：回報錯誤並列出可用名稱 |
| 寶石名稱查無，或本機紀錄沒有遊戲代號 | 不寫入，列入 `not_exported` |
| 寶石比使用者的 PoB 新（PoB 沒收錄） | 工具不讀 PoB 的資料夾，無法事先得知；照常寫入，`notes` 提醒先更新 PoB（實作時修正：原計畫寫「列入 not_exported」做不到） |
| 昇華在 PoB 沒有代號（例如未開放的昇華） | 匯出時不含昇華與昇華天賦，列入 `not_exported` |
| 輔助寶石不能輔助該技能 | 不寫入，列入 `not_exported` |
| 目標天賦查無或到不了 | 不寫入，列入 `not_exported`；其餘照常匯出 |
| `skills` 格式錯誤、超過上限 | 回報錯誤，不產生匯入碼 |
| 職業資料沒有數字代號（尚未重抓） | 回報錯誤並指出要執行 `update passives` |

## 第二段：裝備（2026-11-12 核准）

### 背景

第一段（0.9.0）的匯入碼只有職業、天賦與寶石，沒有裝備，所以 PoB 中攻擊技能顯示為停用，
傷害與防禦也只反映天賦與寶石。第二段把流派建議裡驗證過的裝備與目標詞綴一起寫進匯入碼，
讓 PoB 能算出完整的數字。

你在 2026-11-12 的決定：

- 詞綴數值用**最高階、該階範圍的上限**（例如 `+(100—119) 最大生命` 填 119）。
- 這是假設，要在 README 與匯出說明中寫明；使用者可在 PoB 自行修改。
- 「由使用者指定階級或數值」保留為未來需求，這一段不做。

### 調查結果（PoB 0.23.1 與本機資料，只讀）

| 發現 | 意義 |
|---|---|
| PoB 把裝備當一段文字讀入：稀有度、名稱、基底、`Implicits: N`、一行一條詞綴 | 用標準函式庫組文字即可，不需新的相依套件 |
| 稀有裝備的名稱 PoB 不使用；它靠基底名稱找基底、靠詞綴文字算效果 | 名稱用「POBG + 部位」，不編造像遊戲內的名字 |
| 部位名稱固定：Weapon 1、Weapon 2、Helmet、Body Armour、Gloves、Boots、Amulet、Ring 1、Ring 2、Belt、Charm 1–3、Flask 1–2 | 匯入碼用這些名稱指定每件裝備放哪裡 |
| 我們的基底 1,762 個中 1,749 個在 PoB 同名；傳奇 434 件中 423 件同名 | 絕大多數能直接對上 |
| 一般詞綴 8,745 條：8,118 條是範圍、619 條是固定數字、7 條沒有英文文字 | 範圍取上限；沒有文字的不匯出 |
| 傳奇與基底紀錄已有固定詞綴與傳奇詞綴的文字 | 傳奇不需另外指定詞綴 |
| 現有的 `affix_fact`、`_affix_conflict`（3 前綴 + 3 後綴、同族群只能一條）已能驗證詞綴並回傳最高階 | 直接重用，不另寫一套規則 |

### 設計

**1. `export_pob` 新增參數 `gear`**

每筆一件裝備，格式為 `"部位: 物品; 詞綴; 詞綴"`，中英文皆可：

```
"Weapon 1: Dualstring Bow; Adds # to # Fire Damage; +#% to Critical Damage Bonus"
"Ring 1: Ruby Ring; +# to maximum Life; +#% to Fire Resistance"
"Helmet: 某件傳奇"            （傳奇不寫詞綴）
```

規則（全部由程式依資料處理，不靠模型推論）：

- 部位：上表的名稱，另接受中文（武器、副手、頭盔、胸甲、手套、鞋子、項鍊、戒指 1／2、腰帶、
  護符 1–3、藥劑 1–2）。同一部位只能有一件。
- 物品：基底或傳奇，用現有的物品比對；查無或名稱有歧義的不匯出。
- 物品類別要能放進該部位（例如弓只能放 Weapon 1，箭袋、盾、法器放 Weapon 2，戒指放 Ring 1／2）；
  不符的不匯出。
- 稀有裝備的詞綴：逐條用 `affix_fact` 驗證該基底的類別出得了；每件最多 3 前綴 + 3 後綴、同族群
  一條（與 `verify_build` 相同）。寫入最高階文字，每個範圍取上限。
- 傳奇：寫入紀錄中的固定詞綴與傳奇詞綴，範圍取上限；額外給的詞綴列為未放入。
- 基底的固定詞綴（implicit）一併寫入，範圍取上限。
- 沒放進去的（查無、類別出不了、超過上限、部位不符、沒有英文文字）全部列在 `not_exported`。

**2. 屬性需求把裝備算進去（延續你第一段的要求）**

- 裝備上「+# 力量／敏捷／智慧／全屬性」的詞綴計入「已有屬性」。
- 裝備本身的屬性需求計入「需求」。
- 屬性天賦點的分配因此會考慮裝備；`summary.attributes` 與「要靠裝備補」的說明隨之更新。

**3. 回傳與說明**

- `summary` 增加 `gear`：每個部位放了什麼、幾條詞綴。
- `notes` 增加固定說明：
  - 詞綴用最高階的上限，是理想值；詞綴是隨機的，實際裝備通常較低，可在 PoB 的物品頁修改。
  - 不含品質、符文／靈魂核心、插槽與珠寶。
  - PoB 不認得的基底或詞綴會被它略過或標示為不支援（工具不讀 PoB 的資料夾，事先無法得知）。
- 第一段「需要武器的攻擊技能會顯示停用」的說明，在匯入碼有武器時不再出現。

**4. 流程**

`build_workflow` 與 `poe2-advisor` skill 的第 9 步：呼叫 `export_pob` 時把每個部位驗證過的物品與目標
詞綴用 `gear` 傳入；回答要說明 PoB 的數字是以最高階上限算的理想值。

## 2026-11-12 修訂：匯入碼帶入 PoB 配置（核准）

### 背景

你在 PoB 比較生成的祈願者與 poe.ninja 天梯角色時指出：PoB 的「配置」頁會大幅影響 DPS。
目前匯入碼不寫配置，所以 PoB 算的是「什麼狀態都沒有」的數字（你的截圖是 28,469）；
poe.ninja 的匯入碼則對每個角色一律套用同一組有利假設，兩邊不能直接比。

你在 2026-11-12 的決定：

- 匯入碼**預設要帶入配置**。
- 每一項都要**和流派相符**：流派產生不了暴擊球，配置裡就不該有暴擊球。
- 球類由程式**依資料判斷**，不靠模型推論。
- 球的顆數會影響 DPS，要交代清楚。

### 調查結果（只讀）

| 發現 | 意義 |
|---|---|
| poe.ninja 對每個角色都開：近期暴擊、敵人流血／致盲／冰緩／暈眩／點燃／閃電曝曬；部分角色另開三種球 | 它不看流派是否做得到，所以不能照抄 |
| PoB 的配置是 XML 中一段 `<Config>`，每個項目一行（名稱 + 布林或數字） | 用現有的 XML 組法即可，不需新的相依套件 |
| 球類在 PoB 是 `usePowerCharges` 等開關；開啟後 PoB 用它**自己算出的最大顆數**（基礎值加上天賦與裝備的「+# 最大球數」），另有一格可手動填較少的顆數 | 顆數不必由我們計算，交給 PoB；說明中寫明是以最大顆數計算 |
| 敵人感電等狀態是開關，數值由 PoB 依流派計算 | 只需決定開或不開 |
| 我們的寶石、天賦、裝備文字裡有「會造成某狀態」與「對某狀態的敵人有加成」兩種寫法 | 只有前者能當作「流派做得到」的依據 |

### 設計

**1. 每個配置項目都要有依據才開啟**

依據只來自這次匯出、且已通過驗證的東西：技能與輔助寶石的說明與屬性行、路線上的天賦、裝備上的詞綴。
由程式比對文字，模型不能指定。

| PoB 配置項目 | 開啟條件（流派自己的文字中要有） |
|---|---|
| 使用暴擊球／狂怒球／耐力球 | 有文字說會「獲得／產生／給予」該種球。只提到「消耗」「每顆球」「最大球數」的不算 |
| 敵人感電／點燃／冰緩／冰凍／流血／中毒／致盲／暈眩 | 有文字說會對敵人造成該狀態（例如「擊中時造成流血」「擊中時致盲」「使敵人感電」）。「對已感電的敵人…」這類只是受益的文字不算；「無法造成…」不算 |
| 敵人有閃電／冰冷／火焰曝曬 | 有文字說會造成該種曝曬 |
| 你近期有暴擊 | 流派中有任何一行的效果取決於「近期暴擊」 |

不寫入的項目：敵人的等級、抗性、護甲（沿用 PoB 預設的頭目數值，與 poe.ninja 相同）；任務獎勵中的選擇題；
其他上千個配置項目。

**2. 球的顆數**

開啟後由 PoB 以它算出的最大顆數計算。匯出說明會寫明「以最大顆數計算，可在 PoB 配置頁的『顆數（若非最大）』調整」。
由工具指定較少的顆數，列為保留項目。

**3. 回傳與說明**

- `summary.config`：開了哪些項目，以及每一項的依據（哪顆寶石、哪個天賦或哪件裝備）。
- `notes`：
  - 列出已開啟的項目，並說明 PoB 的 DPS 是在這些狀態下算的。
  - 說明 poe.ninja 對所有角色套用的假設中，哪些因為這個流派沒有依據而沒開，
    所以和天梯數字比較時仍會有落差。
- 匯入碼的備註頁也寫入已開啟的項目。
- 新參數 `config`（預設開啟）：傳 `false` 時不寫任何配置，得到最保守的數字。

**4. 流程**

`build_workflow` 與 `poe2-advisor` skill：回答要列出匯入碼開了哪些配置與依據，並提醒 DPS 是在這些狀態下的數字。
